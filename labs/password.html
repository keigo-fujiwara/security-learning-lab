LAB 02

パスワードとハッシュ演習

不正ログインの多くは、使い回されたパスワードや推測しやすいパスワードが原因です。また、サービス側がパスワードを正しく保存していないと、漏えい時の被害が大きくなります。利用者と開発者の両方の視点で学びましょう。

1. 攻撃者の視点：パスワードはどう破られるか

  • パスワードリスト型攻撃：他サービスから漏えいしたIDとパスワードの組を、そのまま別サービスで試す。使い回しがあると突破される。
  • 辞書攻撃：よく使われるパスワード（password、123456、qwerty など）を順番に試す。
  • 総当たり攻撃：文字の組み合わせを全部試す。短いパスワードほど早く破られる。
  • 漏えいしたハッシュの解析：データベースが盗まれると、攻撃者は手元のPCで高速に試行できる（オフライン攻撃）。

2. 実践：パスワード強度チェッカー

入力した値はこのページの中だけで計算され、どこにも送信・保存されません（本物のパスワードは入力しないでください）。

パスワードを入力すると評価します。

課題1：推定解読時間が「100年以上」になるパスワードを作ろう

ヒント：記号を無理に増やすより、長さが効きます。ランダムな単語を4〜5個つなげる「パスフレーズ」も有効です。

3. 開発者の視点：パスワードの保存方法

Web Crypto API で実際にハッシュを計算して、保存方法による違いを確かめます。

ポイント
  • 平文保存：漏えいした瞬間に全員のパスワードが判明。絶対に避ける。
  • SHA-256のみ：同じパスワードは同じハッシュになるため、「よくあるパスワードのハッシュ表」と照合されるとすぐ判明する。計算も高速なので総当たりにも弱い。
  • ソルト＋低速ハッシュ（PBKDF2 / bcrypt / scrypt / Argon2）：ユーザーごとにランダムなソルトを加えるため同じパスワードでも別の値になり、1回の計算に時間がかかるため総当たりのコストが大幅に上がる。

課題2：確認問題

3つの方式のうち、ハッシュ値を見ただけで「3人が同じパスワードを使っている」と分かってしまうのはどれ？（複数選択）

4. 今日からできる対策

  • パスワードはサービスごとに別のものにする。パスワードマネージャーで管理すると楽。
  • 多要素認証（MFA）やパスキーを有効にする。パスワードが漏れても突破されにくくなる。
  • 開発者は、パスワードを Argon2id / bcrypt / scrypt / PBKDF2 などのパスワード専用ハッシュで保存する。
  • ログイン試行回数の制限や、不審なログインの通知を実装する。
